# Бэкапы и восстановление

Каждая нода кластера 321r ежесуточно готовит согласованные копии своих данных и складывает их в два репозитория на двух других нодах — это рабочая механика правила 3-2-1 ([doctrine-3-2-1.md](doctrine-3-2-1.md)). Снимки шифрует restic, свежесть контролирует маяк, а восстанавливаемость проверяется еженедельно настоящим подъёмом базы из копии. Здесь описано, что именно копируется, по какому расписанию и как вернуть данные.

## Топология: копия на две соседние ноды

- Каждая нода кладёт свой набор на **две другие** ноды (ноды из разных failure-доменов).
- Транспорт — restic по SFTP через меш: `sftp:root@<mesh-ip>:/var/lib/backup-repos/<нода>`.
- Репозитории лежат на принимающих нодах в `/var/lib/backup-repos/<имя-владельца>`.
- Облачных хранилищ нет: только свои VPS и физический носитель владельца.

## Что попадает в набор

| Данные | Как копируется | Примечание |
|---|---|---|
| PostgreSQL | `pg_basebackup` каждого локального инстанса **с текущего первичного через VIP 10.66.0.99** | формат tar со сжатием: `base.tar.gz` + `pg_wal.tar.gz`; две попытки с паузой |
| MongoDB | `mongodump --archive --gzip` каждого локального инстанса | нода-арбитр пропускается — данных нет |
| Конфиги и секреты | `tar` по путям `/etc/db`, `/etc/amnezia`, `/etc/cron.d`, `/etc/systemd/system`, `/opt/pangolin`, `/opt/remnawave`, `/opt/remnanode`, `/opt/db` | собираются по факту наличия |

Промежуточные файлы собираются в `/var/lib/pgbackup`, там же остаются два свежих прогона. Бэкапы запускаются с `nice`/`ionice`: тяжёлый прогон не должен ложно ронять health-checkи сервисов.

Важно: снимок PostgreSQL всегда берётся **с первичного** (через VIP), а не с локального инстанса. Basebackup со стендбая даёт неполный набор WAL, и такая копия не восстанавливается.

## Расписание (cron, `/etc/cron.d/321r`, время UTC)

| Задача | Когда | Где |
|---|---|---|
| `backup-321r.sh` | окно ноды (по умолчанию 03:10, 03:40, 04:10) | каждая нода |
| `backup-beacon.sh` — маяк свежести | ежедневно 09:05 | каждая нода |
| `backup-verify.sh` — верификация восстановлением | воскресенье 05:20 | каждая нода |
| `tg-watch.sh` — дозор | каждый час | каждая нода |
| `tg-export.sh` — выгрузка на физический носитель | 1-го числа 06:05 | каждая нода |
| `tg-digest.sh` — утренний дайджест | ежедневно 09:00 | только control-нода |

Окна разнесены, чтобы ноды не копились одновременно. Свои окна задаются в инвентаре установки: `BACKUP_WINDOWS="a=03:10 b=03:40 c=04:10"`.

Прогон вручную:

```bash
bash /usr/local/bin/backup-321r.sh
tail -n 50 /var/log/backup321r.log
```

## Ретеншн и пароль репозиториев

- После каждого снимка: `restic forget --keep-daily 30 --keep-weekly 12 --keep-monthly 12 --prune`.
- Пароль репозиториев — `RESTIC_PASSWORD` в `/etc/db/secrets/restic.env` (chmod 600). Он один на кластер, генерируется при установке и лежит только на нодах.
- Важно: не пересоздавайте пароль без необходимости — старые копии станут нечитаемы. Распечатайте пароль и храните офлайн ([security.md](security.md)).

## Контроль свежести

- Маяк: успешный прогон пишет метку в `/var/lib/pgbackup/last_ok`. Если бэкапа нет дольше 26 часов, `backup-beacon.sh` шлёт алерт «ПРОТУХ».
- Ошибки прогона приходят в Telegram немедленно («БЭКАП С ОШИБКАМИ» с перечнем этапов).
- Дозор и Zabbix следят за той же меткой со своими порогами ([monitoring.md](monitoring.md), [zabbix.md](zabbix.md)).

## Верификация восстановлением

«Бэкап, который не восстанавливали, не существует». Раз в неделю `backup-verify.sh` для каждого локального репозитория:

1. `restic check --read-data-subset=5%` — целостность данных;
2. восстанавливает последний снимок во временную папку;
3. поднимает scratch-Postgres **из basebackup** и проверяет, что база отвечает и таблицы на месте;
4. проверяет чтение архивов mongo (`gzip -t`) и конфигов (`tar -t`).

Успех пишет метку `/var/lib/pgbackup/last_verify` и шлёт алерт «ВСЁ ВОССТАНАВЛИВАЕТСЯ». Провал — алерт с перечнем упавших проверок. Раз в квартал проводите полный дрилл восстановления ([drills.md](drills.md)).

## Выгрузка на физический носитель

`tg-export.sh` упаковывает набор ноды в `321r-<нода>-<дата>.tar.gz` и отправляет файлом вам в Telegram — сохраните его на физический диск. Это offsite-копия по правилу 3-2-1; ритуал — раз в месяц. Запуск: 1-го числа автоматически или кнопкой «Выгрузить на диск» в боте ([monitoring.md](monitoring.md)). Лимит Bot API — 50 МБ на файл; если набор больше 48 МБ, придёт алерт «нужна нарезка».

## Восстановление: сценарии

### 1. Логическая ошибка (удалены или испорчены данные)

```bash
. /etc/db/secrets/restic.env; export RESTIC_PASSWORD
restic -r /var/lib/backup-repos/<нода> snapshots --compact
restic -r /var/lib/backup-repos/<нода> restore latest --target /tmp/restore
```

Поднимите базу из копии в песочнице (см. рецепт ниже), вытащите нужные данные и верните их в рабочую базу. Для mongo достаточно архива дампа:

```bash
docker run --rm --network host -v /tmp/restore/var/lib/pgbackup:/b mongo:7 \
  mongorestore --archive --gzip /b/mongo-<приложение>-<метка>.archive.gz
```

### 2. Потеряна одна нода

Бэкап здесь — только страховка: данные догоняются репликацией. Ставьте новую ноду штатным путём ([add-node.md](add-node.md), [replace-node.md](replace-node.md)).

### 3. Потеряны все узлы с данными

Новый кластер ставится штатным установщиком ([quickstart.md](quickstart.md)), затем данные возвращаются из снимков restic по рецепту ниже. RTO — часы (зависит от объёма), RPO — время последнего успешного прогона.

### 4. Подъём PostgreSQL из basebackup (точная механика проверки)

```bash
mkdir -p /tmp/pgdata/pg_wal
tar xzf base.tar.gz -C /tmp/pgdata
tar xzf pg_wal.tar.gz -C /tmp/pgdata/pg_wal
rm -f /tmp/pgdata/standby.signal /tmp/pgdata/promote.signal
touch /tmp/pgdata/recovery.signal
cat >> /tmp/pgdata/postgresql.auto.conf <<'EOF'
recovery_target = 'immediate'
recovery_target_action = 'promote'
restore_command = 'false'
EOF
chown -R 70:70 /tmp/pgdata
docker run -d --name restore-pg -v /tmp/pgdata:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=restore postgres:17-alpine \
  -c max_connections=200 -c shared_buffers=32MB
```

Частые ошибки этого рецепта: забытый `pg_wal.tar.gz` (без WAL crash-recovery не проходит), оставленный `standby.signal` и слишком маленький `max_connections` относительно контрольного файла первичного.

### 5. Восстановление с точностью до момента (PITR)

Basebackup + WAL-архив: накладывайте WAL до нужного момента через `recovery_target` вместо `immediate`. Это ручная операция — тренируйте её на дрилле заранее.

## Частые ошибки

- Прогон дублируется, если старые cron-файлы бэкапов остались в `/etc/cron.d/` — штатный расклад даёт единый файл `/etc/cron.d/321r`.
- Ошибку basebackup нельзя проглатывать: без текста ошибки «бэкап не удался» необъясним. Смотрите `/var/log/backup321r.log`.
- Недельные и старшие копии сжимаются restic-ом автоматически; вручную ничего сжимать не нужно.
