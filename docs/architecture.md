# Архитектура

321r — отказоустойчивый кластер VPS любого размера (минимум 3 ноды): сервисы переживают
потерю любого одного сервера, блокировки и смену IP, а полное восстановление занимает
около часа. Этот документ объясняет, зачем всё устроено именно так, из каких слоёв
собран кластер и как запрос доходит до сервиса.

## Задача

1. **Переживать потерю любого одного сервера** — сервисы продолжают работать сами.
2. **Переживать блокировки протоколов и IP** — смену адресов лечит автоматика, не человек.
3. **Восстанавливаться полностью за ~1 час** из git + бэкапов (новый сервер вместо сгоревшего).
4. **Работать без присмотра до месяца** — человек нужен только для физической замены железа.

## Ограничения (от них всё и пляшет)

- Только бесплатное/открытое ПО. Никаких платных сервисов.
- Пользователь в РФ. Cloudflare — только «серое облако» (обычный DNS); оранжевое облако
  и туннели Cloudflare в РФ заблокированы. Протокол WireGuard могут резать по DPI —
  транспорт меша сразу AmneziaWG (обфускация).
- Из РФ — только на свои VPS, из VPS — куда угодно (GitHub, Let's Encrypt, Cloudflare API).
- Секреты — никогда в чат и никогда в git.

## Принципы

1. **Всё находится по DNS-именам, не по IP.** IP — как почтовый индекс: сменился —
   почта всё равно найдёт адресата, потому что «справочник» (DNS) держится в актуальном виде.
2. **Слои независимы**: вход (Pangolin), вычисления (Swarm), состояние (БД), связь (меш) —
   падение одного не валит остальные.
3. **Ни одна копия данных не живёт в единственном экземпляре на ненадёжном ящике.**
4. **Восстановление, а не «дорогая HA»**: git + бэкапы + скрипты дешевле и понятнее
   отказоустойчивого зоопарка.
5. **РФ-нода — гарантированный вход**: её собственный IP блокировать нечем — через неё
   всегда можно попасть в систему из РФ.
6. **БД — «глупые исполнители».** Кто первичный — решает скрипт `db-guard` по голосам
   кластера, движки PostgreSQL/MongoDB лишь исполняют команду.
7. **Данные живут там же, где живёт приложение**: у приложения X — свой набор серверов
   S(X) и никаких чужих копий на чужих дисках.
8. **Узлы — профили, а не имена.** Меш адресуется по `nodes.map`, размещение БД — по
   списку узлов приложения из `/etc/db/apps.d/`, кворумы — формулы от числа узлов
   (⌊M/2⌋+1, правило менеджеров 2K+1). Поэтому кластер масштабируется свободно:
   3 → 5 → 7 → N узлов и обратно, без переделки.
9. **Каждый шаг имеет проверки** — дальше не идём, пока не зелёные.

**Полётное правило: слои не смешиваются.** Машинный трафик (меш, Swarm, БД) не ходит через
VPN-слой; люди не ходят по мешу; вход не зависит от вычислений; состояние не зависит от входа.

## Почему в цепочке 443 и gerbil, и traefik

Gerbil владеет портом 443 (Pangolin, кластерный режим) — это сервер туннелей + SNI-прокси.
Но он закрытая коробка: его таблица маршрутов генерируется панелью Pangolin из БД, он умеет
только «SNI = ресурс → туннель» и «всё остальное → traefik». Traefik — единственный
программируемый переключатель в цепочке: HTTP-роутинг дашборда, ACME-сертификаты,
редиректы и собственные правила маскировки (HostSNI(vpn-*) → Xray, HostSNI(tg) → mtproto).
Схема: gerbil = «кто принимает на 443», traefik = «куда дальше».

## Как течёт запрос к сервису

1. Браузер: `app.<домен>` → DNS (multi-A на все ноды) → любая нода :443.
2. traefik на ноде смотрит SNI (имя) → находит ресурс Pangolin.
3. gerbil определяет, к какой ноде прицеплен туннель сайта (Newt/агент), и пересылает
   туда, если цель здорова (health-check).
4. Newt/агент на целевой стороне стучится в `ip:port` сервиса (localhost, mesh или домашняя сеть).
5. Сервис отвечает; при смерти ноды браузер сам перебирает следующий IP из multi-A.

Ловушки этого пути (404/503/000, health-check'и, сходимость маршрутов) —
в [troubleshooting.md](troubleshooting.md).

## Сети и адреса

- **Меш wg0**: 10.66.0.0/24 (по адресу на ноду), порт 51821/udp, транспорт AmneziaWG 3.1.
- **VIP БД 10.66.0.99/32** назначен на wg0 КАЖДОЙ ноды: приложение ходит на
  `10.66.0.99:<порт>` локально, за ним haproxy (контейнер `db-proxy`) → текущий первичный.
  Адрес не меняется никогда — смена первичного невидима приложениям.
- Публичные порты и таблицы — в [reference.md](reference.md).
- Доверенная зона — меш: `ufw allow from 10.66.0.0/24`, всё остальное — default deny
  плюс DOCKER-USER для контейнерных публикаций.

## Домены сервисов

Каждый публичный сервис — ресурс Pangolin (`app.<домен>`) → сайт-агент (Newt или CLI) →
`ip:port` цели. Сами сервисы запускаются Swarm'ом с ingress-портом: сервис плавает между
нодами, домен этого не замечает. Полная доменная схема — в [reference.md](reference.md),
сертификаты — в [dns-and-tls.md](dns-and-tls.md).

## Служебный слой

- **Komodo** — панель серверов и стеков: Core как swarm-сервис (сам перелетает между
  нодами), periphery (systemd) на каждой ноде, БД — MongoDB RS.
- **Мониторинг** — Uptime Kuma (swarm-стек) + Telegram-алерты; опционально Zabbix HA
  ([zabbix.md](zabbix.md)).
- **Бэкапы** — копии между своими VPS по мешу (без облачных хранилищ), правило 3-2-1
  ([backups.md](backups.md), [doctrine-3-2-1.md](doctrine-3-2-1.md)).
- **Remnawave** — VPN для устройств с маскировкой трафика ([vpn.md](vpn.md)).

Детали слоя БД — в [databases.md](databases.md), меша — в [amnezia-wg.md](amnezia-wg.md),
входа — в [pangolin.md](pangolin.md).
