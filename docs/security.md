# Безопасность

Безопасность 321r строится на простом принципе: наружу открыто ровно то, что должно работать, меш — доверенная зона, а секреты не бывают «немножко утёкшими». Этот документ описывает защиту SSH, firewall, фильтрацию трафика контейнеров и правила обращения с секретами. Проверяйте разделы после каждого изменения инфраструктуры.

## Принципы

1. Наружу открыты только публичные порты сервисов (см. firewall ниже).
2. Меш `10.66.0.0/24` — доверенная зона; всё остальное — default deny.
3. Утёкший секрет считается скомпрометированным и подлежит ротации.
4. Человеческий фактор закрывается 2FA и recovery-кодами офлайн.

## SSH

- Порт **2222**, вход только по ключам: `PasswordAuthentication no`, `PermitRootLogin prohibit-password`, `KbdInteractiveAuthentication no`, `MaxAuthTries 3`.
- Порядок настройки: **сначала подтвердите ключевой вход, потом отключайте пароль**. Иначе можно остаться без доступа. Штатный установщик делает это на шаге `harden`: кладёт ваш ключ в `authorized_keys`, отключает парольный вход и убирает временный порт 22.
- На Ubuntu 24.04 sshd может быть socket-активирован (`ssh.socket` держит только :22 и игнорирует `Port` из конфига). Установщик переводит его на классический `ssh.service` — иначе 2222 не слушается.
- Матрица SSH «все на всех» (по 2222, по ключам) проверяется после каждого изменения кластера.

## fail2ban

Jail `/etc/fail2ban/jail.d/zz-321r.conf`: порты 2 и 2222, `maxretry = 5`, `bantime = 1h`, в ignoreip — localhost, меш `10.66.0.0/24` и адрес установщика. Во время установки jail выключен (чтобы не забанить админа посреди шага), включается на шаге `harden`. Разбан:

```bash
fail2ban-client set sshd unbanip <ip>
fail2ban-client status sshd
```

## Firewall (ufw, default deny)

- Наружу: `80,443,8443,2053,2087/tcp`, `2222/tcp`, `53/udp` с rate-limit, `51820,21820/udp`.
- Меш: `ufw allow from 10.66.0.0/24` — одно правило на доверенную зону.
- Порт 22 открывается только на время установки и закрывается шагом `harden`.
- Профиль S: только 2222 и меш — публичные порты не открывются.
- Зона контейнеров: правила от `172.16.0.0/12` и `10.0.0.0/8` на порты БД 5432:5499 и 27017:27099 (ставит `db-prep.sh`; при выходе порта за диапазон — допишите правило).

## DOCKER-USER (классическая ловушка)

Docker публикует порты **мимо ufw** — фильтрует только цепочка `DOCKER-USER`. Политика (`scripts/docker-user.sh`): established/related, bridge- и mesh-сети, loopback — пропустить; публичные порты TCP `80 443 8443 2053` и UDP `53 21820 51820` — пропустить; остальным — DROP. Для IPv6 — зеркало.

Важно: DOCKER-USER видит пакеты **после DNAT** — порт здесь контейнерный, а не host-маппинг. Публикация `8443:3000` блокируется, если в белом списке стоит `8443`, а виден `3000`. Сверяйтесь по порту контейнера.

Фенсинг использует ту же цепочку: при потере кворума в позицию 1 вставляются DROP-правила изоляции ноды. Частая ошибка: повторный запуск `docker-user.sh` **стирает** правила фенса — при ручных работах учитывайте это.

## Сетевые принципы

- Адреса баз (VIP 10.66.0.99) — приватный диапазон: наружу недостижим, каждая нода отдаёт его только своим контейнерам.
- MongoDB работает без авторизации — осознанно, только внутри меша. При выходе за пределы меша — обязательно включайте авторизацию.
- UI панелей наружу не выносится: доступ только через ресурсы Pangolin (HTTPS + свои сертификаты).
- Из РФ идите только на свои VPS: не тащите секреты через заблокированные сервисы.

## Секреты

| Правило | Детали |
|---|---|
| Никогда в чат и никогда в git | открытые секреты в репозиторий не попадают |
| Живут на нодах | `/etc/db/secrets/*.env`, `umask 077`, chmod 600 |
| Секреты установки | `install/secrets/` (ключ кластера, пароли) — в git никогда |
| В git — только зашифрованные | SOPS (age): `secrets/*.enc.yaml`; ключ age — в менеджер паролей + печать офлайн |
| Вывод с секретами маскировать | `sed "s/[A-Za-z0-9_-]\{20,\}/СКРЫТ/g"` перед показом |
| Ротация | при утечке — немедленно: токены, пароли, HeaderProtectionKey меша |

Памятка владельца (все пароли, ключи и ссылки одним файлом) собирается командой `bash install/handover.sh`: файл кладётся в `/root/` (chmod 600) и отправляется вам в Telegram. Сохраните её в менеджер паролей и распечатайте.

Важно: ключ доступа, который когда-либо проходил через чат или переписку, считается скомпрометированным — замените его до начала работы.

## Аудит

```bash
ufw status verbose
iptables -L DOCKER-USER -n --line-numbers
nmap -p- <соседняя-нода>    # сверить с таблицей открытых портов
```

- Проводите аудит после каждого изменения и перед публикацией чего-либо наружу.
- Ищите открытые секреты в git перед публикацией репозитория.
- Сверяйте список слушающих портов: `ss -tlnup` не должен показывать ничего сверх политики.
