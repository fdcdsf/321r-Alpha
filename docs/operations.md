# Эксплуатация и сценарии отказов

Кластер спроектирован так, что большинство сбоев закрывает автоматика: переключение баз,
перенос задач, обновление DNS, лечение зависших контейнеров. Этот документ описывает
регулярные процедуры, что происходит при отказах без вашего участия и что делать человеку.
Поиск проблемы по симптому — [troubleshooting.md](troubleshooting.md), учения — [drills.md](drills.md).

## Что делает автоматика (без человека)

| Процедура | Период | Что делает |
|---|---|---|
| `ddns.sh` | каждые 2 мин и после ребута | обновляет A-записи при смене IP ноды |
| `reresolve-dns` | 45 с | переподключает пиров меша на новый IP |
| `db-guard` | 10 с | назначает первичного БД, переключает прокси VIP, фенсит изолированные ноды |
| `unhealthy-restart.sh` | 1 мин | перезапускает контейнеры в статусе unhealthy |
| `pangolin-wildcard-repair.sh` | 30 мин и после старта pangolin | лечит wildcard-сертификаты и DNS-записи |
| `tg-watch.sh` (дозор) | 1 час | диск, память, нагрузка, сертификаты маски, свежесть бэкапа и верификации; алерт в Telegram |
| `backup-321r.sh` | ночью по окнам (по умолчанию 03:10/03:40/04:10 UTC) | restic-снимки и дампы БД на 2 соседние ноды |
| `backup-beacon.sh` | 09:05 UTC | алерт, если свежего снимка нет дольше 26 часов |
| `tg-digest.sh` | 09:00 UTC (control-нода) | утренняя сводка по кластеру |
| `backup-verify.sh` | вс 05:20 UTC | верификация восстановления: restic check, restore, smoke-тест PG |
| `tg-export.sh` | 1-го числа 06:05 UTC | выгрузка копий вам в чат для записи на физический носитель |

Подробно о бэкапах — [backups.md](backups.md), о дозоре и алертах — [monitoring.md](monitoring.md).

## Регулярные процедуры (человек)

| Когда | Что | Время |
|---|---|---|
| Ежесуточно | прочитать дайджест и алерты в Telegram | 1 мин |
| Еженедельно | взгляд на логи бэкапов (`/var/log/backup321r.log`), «тишина в алертах» | 5 мин |
| Ежемесячно | проверить алерт-канал (намеренно сломать тестовый ресурс); `free -h` и место на дисках; 2FA и recovery-коды | 15 мин |
| Ежеквартально | дриллы: смена IP, промоушен PG, назначение Mongo, фенсинг, «нода ложится», восстановление из бэкапа ([drills.md](drills.md)) | час |
| Раз в полгода | ребут-тест всех серверов ([drills.md](drills.md)) | час |
| Раз в год | решить по бесплатным VPS: продлить или убрать ([remove-node.md](remove-node.md)) | — |
| Перед любыми изменениями | `git commit`; секреты — только через SOPS | правило |

## Автоприёмка и памятка владельца

После установки и после любых крупных изменений прогоняйте автоприёмку:

```bash
./install.sh --check          # или: bash install/install-check.sh
```

Проверяются: ssh-порт 2222 и ключевой вход, ufw и fail2ban, пинги меша и VIP, Swarm,
«ровно один первичный» по каждой БД, db-guard, репозитории бэкапов, бот, аварийный режим,
сертификаты дашборда, Newt-сайты, Remnawave, Zabbix. Код выхода 0 — все критичные проверки
пройдены. Любое `✗` — чините и повторяете прогон.

Шаг `handover` собирает все пароли, ключи и ссылки в памятку владельца:
`/root/321r-pamyatka-<дата>.txt` (права 600, копия на control-ноде) и отправляет файл вам
в Telegram. Всё содержимое памятки — секреты: сохраните в менеджер паролей или
распечатайте офлайн. В git и облака памятку не класть.

## Сценарии отказов

### Смена IP ноды

- **Само (≤2 мин):** `ddns.sh` обновляет A-записи, `reresolve` переподключает пиров меша,
  агенты уходят на живые ноды.
- **Человек:** ничего; проверить `wg show` и открыть панель Pangolin.

### Блокировка IP ноды

- **Само:** вход из РФ идёт через ноды с «не блокируемыми» адресами (multi-A); изолированная
  нода получает фенс (нет кворума >60 с → DROP в DOCKER-USER): данные целы, нода молчит,
  большинство продолжает писать.
- **Человек:** сменить IP у провайдера ([replace-node.md](replace-node.md), случай смены IP);
  для людей блокировки делает незаметными VPN-слой ([vpn.md](vpn.md)).
- Важно: запись с изолированной ноды в период изоляции невозможна — это осознанный CP-режим.

### Потеря одной VPS

- **Само (секунды–2 мин):** Swarm переносит задачи (включая Core Komodo); db-guard голосует
  и назначает нового первичного; прокси переключаются — приложения пишут дальше (адрес VIP
  не менялся); кластер жив на N−1.
- **Человек (~1 час):** новая VPS и процедура [replace-node.md](replace-node.md).
- Потеря ACME-ноды: ACME временно выключен, сертификаты живут в БД; при замене включить
  `enable_acme_client` на одной живой ноде ([dns-and-tls.md](dns-and-tls.md)).

### Потеря ноды первичного БД

- **Само (≤2 мин):** следующий по цепи промоутирован (PG) или назначен (Mongo), прокси на
  всех нодах переключились, метки Swarm обновлены. RPO — последние секунды (асинхронная
  репликация).
- **Человек:** как при потере VPS (данные догонятся репликацией); дампы — страховка от
  логических ошибок ([backups.md](backups.md)).
- Вернувшийся старый первичный штатно становится стендбаем за ~1 мин; если таймлайн
  разошёлся — `pg-rebuild-standby.sh` ([databases.md](databases.md)).

### Потеря двух VPS (худший случай)

- **Само:** кворума нет → db-guard фенсит выжившую ноду (данные целы, CP-режим).
- **Человек (часы):**

```bash
# на выжившей ноде:
docker swarm force-new-cluster
iptables -L DOCKER-USER -n --line-numbers   # снять фенс-правила DROP (позиция 1)
iptables -D DOCKER-USER 1
```

1. Поднять стеки из git.
2. Данные: basebackup+WAL с репозиториев на соседних нодах, дампы — [backups.md](backups.md).
3. Новые ноды — [add-node.md](add-node.md), затем шаги `db` и `check` установщика.
- Готовность подтверждается квартальным дриллом восстановления — без дрилла это теория,
  а не обещание ([drills.md](drills.md)).

### Аварийный режим (потеря большинства)

- db-guard фенсит выжившую ноду и ждёт команды владельца: `/survival` в Telegram-боте или
  `survival.sh` на выжившей ноде.
- Предохранитель: если через VIP отвечает живой первичный — ничего не меняется.
- Цена режима: потеря последних записей. Возврат — строго «шаг назад» или пересборка
  стендбаев `pg-rebuild-standby.sh` ([troubleshooting.md](troubleshooting.md)).

## Правила человеческого вмешательства

1. Сначала смотрим, само ли чинится (2–5 мин): db-guard, Swarm, ddns, repair-cron —
   большинство сбоев закрывает автоматика.
2. Блоки команд выполняйте одним куском из одного терминала; первая строка блока проверяет
   ноду (`hostname`, `docker node ls`) — чтобы команда не ушла не на тот сервер.
3. Каждое действие с БД — через VIP `10.66.0.99`; после любых действий с pangolin дождитесь
   repair-цикла или запустите `pangolin-wildcard-repair.sh` вручную.
4. После разбора зафиксируйте: что случилось, что чинили, что автоматизировать. Новый сбой —
   новый пункт в [troubleshooting.md](troubleshooting.md) и правило в установщик.
