# Базы данных: слой БД

Слой БД одинаков для всех приложений: PostgreSQL или MongoDB, репликация между нодами и постоянный адрес через VIP `10.66.0.99`. Кто первичный, решает не движок, а db-guard — автоматика кластера, которая переживает отказы узлов без участия человека. Здесь — реестр приложений, развёртывание, фейловер, пересборка стендбаев и правила эксплуатации.

См. также: [Добавление ноды](add-node.md), [Удаление ноды](remove-node.md), [Бэкапы](backups.md), [Troubleshooting](troubleshooting.md).

## Модель одной картинкой

- **Один инстанс = одно приложение.** БД приложения X живут только на узлах S(X) из `/etc/db/apps.d/<app>.yaml`; чужих баз на чужих дисках нет.
- **Адрес приложения вечен**: `10.66.0.99:<port>` (VIP на каждой ноде). За VIP — локальный haproxy (контейнер `db-proxy`) → текущий первичный. Приложение никогда не перепривязывается, смена первичного невидима.
- **db-guard** (systemd-таймер каждые 10 с на каждой ноде) назначает первичного, переключает прокси и изолирует ноду без кворума. В штате молчит.
- PG: streaming primary/standby, промоушен через `pg_ctl promote`. Mongo: реплика-сет, но назначение наше (priority 1 назначенному, 0 остальным).
- **Фенсинг**: нет кворума Swarm дольше 60 с → DROP в DOCKER-USER — изолированная нода молчит, данные целы; большинство пишет (осознанный выбор в пользу доступности записи).

## Реестр приложения: /etc/db/apps.d/<app>.yaml

Декларация без секретов. Секреты генерируются на нодах в `/etc/db/secrets/<app>.env` (umask 077) и в git не попадают. `db-add` клонирует реестр на все ноды — db-guard читает его для голосов даже вне S(X).

```yaml
# /etc/db/apps.d/billing.yaml
name: billing
engine: pg              # pg | mongo
class: cluster          # cluster | local (без репликации и прокси, инстанс прямо на VIP)
placement: [a, b, c]    # S(X): где живут БД приложения
primary: a              # стартовый первичный; дальше назначает db-guard
port: 5434              # порт приложения на VIP 10.66.0.99 (реестр = диспетчер портов)
```

```yaml
# /etc/db/apps.d/catalog.yaml
name: catalog
engine: mongo
class: cluster
placement: [b, c]
primary: b
port: 27018
arbiter: a              # арбитр на отдельном узле: при |S|=2 без него нет мажоритары
```

| Поле | Смысл |
|---|---|
| `name` | имя приложения (и базы, и контейнеров `pg-<app>` / `mongod-<app>`) |
| `engine` | `pg` или `mongo` |
| `class` | `cluster` — репликация + прокси; `local` — одиночный инстанс на VIP |
| `placement` | узлы S(X), где живут данные (порядок списка = цепь назначений) |
| `primary` | стартовый первичный (обязательно внутри `placement`) |
| `port` | порт приложения на VIP: PG 5432+, Mongo 27017+ |
| `arbiter` | только mongo при \|S\|=2: узел арбитра вне placement |

Важно: `port` — диспетчер портов, у каждого приложения свой (например, pangolin 5432, remnawave 5433, zabbix 5434). Диапазоны ufw для контейнеров — 5432:5499 и 27017:27099; при выходе за них допишите правило в `db-prep.sh`.

## Развёртывание: db-add.sh

```bash
bash /usr/local/bin/db-add.sh <app>    # с менеджерской (control) ноды
```

Что делает само: клонирует реестр на все ноды; генерирует секреты на первичном и раздаёт узлам S(X); PG — контейнер `postgres:17-alpine`, роли и база, `pg_hba` для меша, JIT выключен; стендбай(ы) — `pg_basebackup -R`; Mongo — `mongod --replSet`, `rs.initiate` (priority 1 стартовому первичному, арбитр — `arbiterOnly`); блок haproxy на **всех** нодах (адрес VIP:порт обязан работать везде); метки Swarm `svc.<app>` и `db-primary-<app>`.

Повторный запуск безопасен: где данные уже есть, basebackup пропускается — доделываются только новые узлы. Mongo так же: `db-add` сверяет состав реплика-сети с `placement` и докладывает недостающих членов (данные догоняются сами); сузить состав — `app-member remove`.

## db-guard: назначение и фейловер

Каждый тик (10 с) для инстансов своей ноды: проверка первичного → голоса менеджеров → назначение → перевешивание прокси → шаг назад старого первичного → фенс при потере кворума. Гонки двух промоушенов нет: первичным становится только следующий по цепи placement.

- Голос: каждая нода пишет метку `vote.<app>.<алиас>=<0|1>` (свежесть 45 с); «мёртв» — после двух подряд неудачных проверок. Когда голосов «мёртв» ≥ половины менеджеров + 1 — первичный объявлен мёртвым.
- Назначение: PG — `pg_ctl promote` + переключение прокси; Mongo — `priority 1` назначенному (без первичного — `force`-reconfig). Метка `db-primary-<app>` живёт только на узле первичного.
- Старый первичный сам уходит в стендбай (переписывает `primary_conninfo`, `standby.signal`, рестарт); вернувшийся стендбай перевешивается на текущего первичного.
- Фенс: DROP в DOCKER-USER рвёт и меш, и локальный путь приложение → haproxy → первичный (изолированный первичный не принимает записи). Кворум вернулся — правила снимаются, стендбаи догоняют по WAL.

```bash
journalctl -t db-guard -n 30 --no-pager
# маркеры: ПРОМОУШЕН, метка перехвачена, СТАРЫЙ ПЕРВИЧНЫЙ, апстрим прокси →,
#          ФЕНС / ФЕНС снят, стендбай перевешан, мой инстанс не отвечает
```

Ручные режимы: `db-guard.sh --claim-now <app> <узел>` (перенос метки) и `db-guard.sh --survival-now` (аварийный подъём). Аварийный режим при потере большинства настраивается в `/etc/db/cluster.yml` (`survival: policy: manual-via-bot | auto | off`): вручную — команда `/survival` в Telegram-боте или `survival.sh` на выжившей ноде. Предохранитель: если через VIP отвечает живой первичный — ничего не меняется. Цена режима — потеря последних записей; после возврата кворума обязательна сверка целостности («шаг назад», пересборка стендбаев).

## Пересборка стендбая PostgreSQL

Симптом: `pg-<app>` крашится в цикле, в логе `FATAL: requested timeline N is not a child of this server's history`. Это не авария: после фейловеров кластер сменил таймлайн, а диск стендбая отстал.

```bash
/usr/local/bin/pg-rebuild-standby.sh <app>    # на узле со стендбаем; по умолчанию app=pangolin
```

Скрипт останавливает инстанс, чистит PGDATA и WAL, делает `pg_basebackup` с первичного через VIP (порт берётся из реестра) и поднимает стендбай. Данные не теряются, занимает ~1 минуту.

## Перенос и состав группы: app-move / app-member

```bash
/usr/local/bin/app-move.sh <app> <откуда> <куда>     # перенос инстанса на другую ноду
/usr/local/bin/app-member.sh add <app> <узел>        # добавить инстанс в группу
/usr/local/bin/app-member.sh remove <app> <узел>     # убрать инстанс (данные остаются на диске)
```

`app-move` готовит целевую ноду (секреты и compose), копирует данные через VIP, меняет `placement` на всех нодах; если уезжал первичный — плановый фейловер (промоушен цели, перенос метки, проверка VIP): клиенты видят паузу 10–20 секунд. `app-member` защищён: нельзя убрать последний инстанс группы и нельзя убрать первичный (сначала перенос). PostgreSQL и MongoDB обслуживаются одинаково: у Mongo новый член вступает в реплика-сет и догоняет данные сам (initial sync), плановый фейловер — через приоритеты и `stepDown`. Те же действия есть в Telegram-боте: «🧩 Приложения» → приложение → «🧩 Инстансы БД».

## Mongo: арбитр и состав реплика-сети

При |S|=2 арбитр (`arbiter: <узел>`) даёт мажоритару без данных: у него `arbiterOnly` и тот же лимит памяти 640m. Состав реплика-сети правит тот же `app-member`/`app-move`, что и у PostgreSQL; прямая команда для редких случаев:

```bash
/usr/local/bin/mongo-rs.sh status <app>                 # состав и статусы
/usr/local/bin/mongo-rs.sh add <app> <mesh-ip>:<порт>   # добавить члена (данные копируются сами)
/usr/local/bin/mongo-rs.sh remove <app> <mesh-ip>:<порт> # убрать члена
```

`mongo-rs.sh` сам находит первичного; `placement` в реестре меняется отдельно (поэтому удобнее `app-member` — он делает и то, и другое, и обновляет блок прокси на всех нодах командой `db-proxy-sync.sh <app>`).

Проверки и правки mongosh — только отдельным контейнером; `docker exec` с mongosh внутри контейнера mongod убивает базу по OOM:

```bash
# статус реплика-сети
docker run --rm --network host mongo:7 mongosh \
  "mongodb://10.66.0.99:27017/?replicaSet=rs_catalog" --quiet \
  --eval 'rs.status().members.map(m => m.name + ":" + m.stateStr)'
```

«Зависший» или отставший член пересоздаётся так же просто, как стендбай PostgreSQL: `app-member remove <app> <узел>` и тут же `app-member add <app> <узел>` — данные догонятся сами.

## Правила эксплуатации

| Правило | Почему |
|---|---|
| Писать в БД **только через VIP** `10.66.0.99` | на стендбай — `read-only transaction`; записи мимо VIP расходятся с реальностью |
| `max_connections=200` (не 20) | пулы панелей душат 20 слотов → каскадный отказ |
| mongosh — только отдельным контейнером `docker run --rm --network host mongo:7 mongosh ...` | `docker exec` внутрь mongod убивает базу по OOM |
| Прокси перезагружать `docker restart db-proxy` | `docker kill -s USR1` для Docker = «остановлен», контейнер не поднимется |
| Возврат старого первичного = пересборка basebackup (~1 мин) | журнал уезжает вперёд точки раскола — это штатно |
| Расхождение таймлайна → `pg-rebuild-standby.sh` | штатное лечение, не авария |
| Зависший/отставший член Mongo → `app-member remove` + `add` | первая синхронизация делает всё сама |
| Миграции БД — одной задачей | параллельный DDL с разных нод мешает сам себе |
| Лимиты памяти обязательны: PG `mem_limit` 512m, Mongo 640m минимум даже арбитру | cgroup OOM-киллер убивает бэкенды → crash-recovery и 57P03 у панелей |
| Кэш Mongo ниже 0.25 не ужимать (`wiredTigerCacheSizeGB`) | mongo не стартует (`BadValue`, crash-loop); экономия — только через `mem_limit` |
| JIT в наших БД выключен (`ALTER DATABASE <app> SET jit = off`, вшито в db-add) | монстр-планы на слабых нодах дают таймауты вместо 20 мс |
| `ANALYZE` после крупных правок руками | битая статистика приводит к чудовищным планам |
| Логи докера ограничены (logrotate) | болтливые проверки наращивают json.log до гигабайтов |

## Полезные команды

```bash
# кто первичный (PG):
docker exec -u postgres pg-<app> psql -U postgres -tAc "SELECT pg_is_in_recovery()"
# реплики:
docker exec -u postgres pg-<app> psql -U postgres -tAc \
  "SELECT application_name, client_addr, state FROM pg_stat_replication"
# подключение через VIP:
. /etc/db/secrets/<app>.env
docker exec -e PGPASSWORD="$POSTGRES_PASSWORD" pg-<app> psql -h 10.66.0.99 -p 5432 -U postgres
# метки Swarm (кто назначенный первичный):
docker node inspect <имя-в-swarm> --format '{{json .Spec.Labels}}'
```
