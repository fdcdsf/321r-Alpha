# Доктрина 3-2-1

Продукт 321r назван в честь правила бэкапирования 3-2-1, и это правило положено в основу всей эксплуатации кластера. Доктрина описывает, как кластер переживает отказы, как ведёт себя в аварийном режиме и какими действиями управляет владелец. Соблюдение этих правил важнее любых отдельных настроек.

## Правило 3-2-1 → механика продукта

| Правило | Трактовка в 321r |
|---|---|
| **3** копии | живая реплика в кластере + бэкап на двух соседних нодах + выгрузка на физический носитель |
| **2** носителя | ноды территориально разнесены и у разных провайдеров + физический диск владельца |
| **1** offsite | физический носитель владельца (ежемесячная выгрузка через Telegram-бота) |

Копии каждой ноды лежат минимум на двух других узлах из разных failure-доменов. Секреты бэкапов (пароль restic) хранятся офлайн — распечатка ([backups.md](backups.md)). Бэкап — страховка от логических ошибок, а не основное хранилище данных: плохой `DELETE` применяется мгновенно, а бэкап — нет.

## Отказоустойчивость: N = 2K+1 и лестница деградации

| Потеряно | Режим | Цена |
|---|---|---|
| ≤ K узлов (1 из 3, 2 из 5) | полная функция: кворум, консистентность, RPO ≈ 0 | нет |
| > K, но данные выжили | аварийный режим: выживший поднимается принудительно | потеря последних транзакций, риск split-brain при возврате «мёртвых» |
| почти всё | остаточное выживание: VPN/туннели по кешу, доступны копии 3-2-1 | восстановление из бэкапов, RTO ~1 ч |

## Аварийный режим

По умолчанию (`cluster.yml` → `survival: {policy: manual-via-bot}`) аварийный режим включает **владелец**: при потере кворума бот присылает алерт с предложением поднять выжившие инстансы. Включение — кнопка или команда `/survival` в боте, либо запуск на выжившей ноде:

```bash
bash /usr/local/bin/survival.sh
```

- Предохранитель fail-safe: если через VIP отвечает живой первичный — ничего не меняется. Неизвестность = не трогаем.
- Политика `survival: {policy: auto, auto_after: 30m}` в `cluster.yml` — для необслуживаемых установок; `off` — никогда не поднимать.
- Аварийный старт всегда оставляет громкое событие в журнале и в алертах ([monitoring.md](monitoring.md)).

Важно: цена режима — потеря последних записей и риск split-brain. Включайте, когда альтернатива — простой сервиса.

## Правило возврата: «шаг назад»

При оживлении «мёртвых» нод **никакого авто-слияния не бывает**. Порядок возврата:

1. Сверить таймлайны: нода, на которой были «лишние» записи, делает шаг назад.
2. Стендбаи с расхождением таймлайна пересобираются штатным скриптом:

```bash
bash /usr/local/bin/pg-rebuild-standby.sh <приложение>
```

3. Только после этого кластер возвращается к кворумной работе.

Нарушение этого правила — единственный способ потерять данные, которые кластер до того держал целыми.

## Telegram-бот: три роли, один канал

1. **Управление**: панель на кнопках — статус, сервисы, приложения, контейнеры, базы, серверы, логи, действия. Опасные действия — только через экран подтверждения.
2. **Алерты**: события db-guard (ПРОМОУШЕН, ФЕНС, аварийный режим), свежесть бэкапов, дозор, Zabbix. Алерты шлёт любая нода, команды принимает control-нода ([monitoring.md](monitoring.md)).
3. **Транспорт offsite**: выгрузка бэкапов владельцу в чат для записи на физический носитель.

Детали и безопасность бота — в [monitoring.md](monitoring.md) и [security.md](security.md).

## Живая миграция приложений

Приложения не знают, где живёт база: они ходят на VIP 10.66.0.99, а первичного назначает db-guard. Поэтому перенос инстанса не требует остановки приложения.

| Тип | Как переносится | Даунтайм |
|---|---|---|
| БД-кластер (pg/mongo) | новый член на целевой ноде → синхронизация → плановый промоушен → вывод старого | секунды |
| Stateless (панели, subpage) | поднять на новой → перевесить трафик → остановить старую | ~0–30 с |
| Singleton (valkey и т.п.) | поднять новый → переключить потребителей → остановить старый | секунды–минута |

Инструменты ([deploy.md](deploy.md), [operations.md](operations.md)):

```bash
bash /usr/local/bin/app-move.sh <приложение> <откуда> <куда>     # перенос инстанса
bash /usr/local/bin/app-member.sh add <приложение> <нода>        # добавить инстанс
bash /usr/local/bin/app-member.sh remove <приложение> <нода>     # убрать инстанс
```

Те же действия доступны кнопками в карточке приложения в боте. Защита: нельзя убрать последний инстанс группы и нельзя убрать первичный — сначала перенос. Данные после переноса остаются на диске до ручной очистки. Перенос `app-move` поддержан для PostgreSQL; mongo переносится иначе ([databases.md](databases.md)).

## Верификация и дриллы

- Еженедельная верификация восстановлением — обязательна ([backups.md](backups.md)).
- Маяки свежести: протухание бэкапа — громкий алерт.
- Квартальные дриллы: полное восстановление из offsite-копии с замером RTO, «потеря большинства» (аварийный режим), миграция приложения ([drills.md](drills.md)).

## Манифест кластера

`cluster.yml` — источник правды о составе серверов, размещении приложений и политике выживания. Копия лежит на нодах в `/etc/db/`, секретов в нём нет. Приложения описывают требования («3 реплики в 2 доменах»), а не конкретные ноды. Команды `cluster.sh status` и `cluster.sh apply` сверяют манифест с реальностью и разкладывают его по нодам ([architecture.md](architecture.md)).

## Метрики доктрины

RTO и RPO — не обещания, а измеренные величины: фиксируйте их по итогам каждого дрилла ([drills.md](drills.md)). Каждый аварийный старт, промоушен и фенс оставляет событие в журнале и в алертах — по ним восстанавливается ход аварии.
