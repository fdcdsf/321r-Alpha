# Замена сервера: смена IP, блокировки, потеря, переезд железа

Четыре разных случая, которые часто путают. В первых двух сервер вообще не меняется, в третьем — меняется быстро (новая VPS вместо старой примерно за час, данные догоняются сами), четвёртый — плановый переезд роли без окна недоступности. Домен в примерах — `<base>` (например, `example.com`).

См. также: [Добавление ноды](add-node.md), [Удаление ноды](remove-node.md), [Эксплуатация и отказы](operations.md).

## Какой случай у вас?

```text
Сервер отвечает, но IP другой?       → случай 1 (ничего делать, ждать до 3 минут)
Из одной сети не открывается,       → случай 2 (блокировка IP)
из другой всё работает?
Сервер молчит совсем?                → случай 3 (потеря → замена)
Хотите переехать на лучшее железо?   → случай 4 (плановая замена)
```

## Случай 1. IP сервера сменился (провайдер)

Автоматика чинит за ≤3 минут, руками обычно ничего:

1. `ddns.sh` (cron каждые 2 мин) правит A-запись `<alias>.<base>` и свою строку в хабе `dns.<base>`.
2. `reresolve-dns.sh` (таймер 45 с) переподключает пиры меша к новому IP — если их endpoint'ы заданы именами `<alias>.<base>:51821`. Если endpoint'ы по IP — перегенерируйте меш шагом `mesh` установщика.
3. Pangolin держит список доверенных адресов в конфиге: повторите шаг `pangolin` — он пересчитает `trusted-upstreams` и `base_endpoint` по инвентарю.

Проверить после: `awg show wg0` — рукопожатие свежее; `curl -sk https://pangolin.<base>/` = 200.

## Случай 2. IP заблокировали (провайдер или реестр блокировок)

Симптомы: из одной сети не открываются дашборд и ресурсы по этому IP (по другим IP из multi-A — открываются), пинги и рукопожатия к ноде не идут; из другой сети всё работает.

Что происходит само: клиенты перебирают IP из multi-A, вход идёт через незаблокированные ноды; агенты сайтов (Newt) сами уходят на живые узлы за секунды.

Что делать человеку — по нарастанию:

1. Убедиться, что остальное доступно: `curl -sk --resolve pangolin.<base>:443:<живой-IP> https://pangolin.<base>/`.
2. Потребовать у провайдера смену IP → дальше случай 1 (автоматика).
3. Если провайдер не меняет — заказать новый сервер и перенести роль (случай 3).
4. Запасные пути для людей: VPN-слой Remnawave ([vpn.md](vpn.md)) обходит блокировки по IP; запасные порты дашборда 8443 и 2053; маскировка трафика — [amnezia-wg.md](amnezia-wg.md).

Если начали резать протокол, а не IP, — порядок деградации транспорта меша: AmneziaWG → обычный WireGuard → xray-туннель; рецепты в [amnezia-wg.md](amnezia-wg.md).

## Случай 3. Сервер потерян — замена новым

Цель: новая VPS вместо старой за ~1 час, данные догоняются репликацией. Если потерян один узел из многих — RPO секунды.

1. **Убрать мёртвое тело**: `docker node rm --force <старое-имя>` с живой ноды; вычистить упоминания по шагу 3 [remove-node.md](remove-node.md) (`nodes.map` на всех ★, `apps.d`, сайт-агент). **DNS-записи НЕ удалять** — они переедут на новый сервер.
2. **Новая VPS** (та же юрисдикция и роль — предпочтительно): добавить её в инвентарь **с тем же именем и тем же mesh-адресом** — система считает её «вернувшимся домом» — и повторить шаги установщика по [add-node.md](add-node.md), шаги 1–2.
3. **DNS**: A-запись `<alias>.<base>` и строку в хабе `dns.<base>` переписать на новый IP (ddns сделает это сам и будет поддерживать).
4. **Swarm**: join менеджером (шаг `swarm` делает сам), метки роли проставляются по инвентарю.
5. **Данные**: `bash /usr/local/bin/db-add.sh <app>` для каждого приложения, где узел есть в `placement`, — PostgreSQL догоняет через `pg_basebackup`, данные появляются сами. Mongo — вручную (`rs.add`). Если нода была первичной — db-guard уже назначил другую (≤2 мин); вернувшаяся станет стендбаем.
6. **Pangolin**: шаг `pangolin` (рендер конфигов, compose up, сайт-агент `cluster-<alias>` заново) и обязательно `pangolin-wildcard-repair.sh <новый-IP>` после старта.
7. **Komodo**: periphery с ключом onboarding (шаг `komodo`).
8. **Если погибла ACME-нода** (на ней включён `enable_acme_client`): включить его на одной живой ноде (только на одной!) и перезапустить её Pangolin; сертификаты живут в PostgreSQL и восстановятся сами. После рестарта — repair из пункта 6.
9. Приёмка: `./install/install.sh --check` плюс чек-лист [add-node.md](add-node.md).

| Шаг | Время |
|---|---|
| установка ноды шагами `base`–`db` | 10–20 мин |
| Swarm join и метки | 2 мин |
| db-add (basebackup) | 5–15 мин по объёму БД |
| Pangolin + repair + агент | 10 мин |
| проверки | 5 мин |
| **Итого** | **~1 час** |

## Случай 4. Плановая замена железа (старый сервер жив)

Самый безопасный путь: переезжает роль, а не авария; окно недоступности — ноль.

1. Добавить новый сервер как ноду ([add-node.md](add-node.md)) — кластер растёт.
2. Перевести на неё роли старой:
   - БД: расширить `placement` на новый узел → `db-add.sh <app>` (догонит) → сузить `placement` со старого (для Mongo — `rs.remove`); либо перенос одной командой `app-move.sh <app> <откуда> <куда>` ([databases.md](databases.md));
   - метки и роли Swarm переставить по инвентарю; ACME-роль — если была на старой ноде;
   - сайт-агент Pangolin пересоздать на новой ноде.
3. Убрать старый сервер по [remove-node.md](remove-node.md).
4. DNS: A-запись постепенно переставить на новый IP (ddns подхватит).

## Кто что чинит сам

| Событие | Автоматика | Человек |
|---|---|---|
| Смена IP | ddns (≤2 мин), reresolve для пиров с именными endpoint'ами (≤45 с) | ничего или перегенерация меша/конфигов Pangolin |
| Блокировка одного IP | перебор IP из multi-A, уход агентов на живые ноды | смена IP у провайдера или новая VPS |
| Потеря одного сервера | Swarm переносит задачи, db-guard назначает первичного, кластер жив на N-1 | поставить новую VPS (случай 3) |
| Потеря двух и более серверов | фенсинг сохраняет данные, но кворума нет | аварийное восстановление: [operations.md](operations.md) |
