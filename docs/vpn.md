# VPN (Remnawave) и маскировка

Кластер «321r» выдаёт VPN через Remnawave: панель управления, нода Xray на каждом сервере и страница подписок. Трафик VPN и Telegram-прокси спрятан за маскировкой: порт 443 каждой ноды выглядит для проверяющего как обычный сайт с настоящим сертификатом. Здесь описано подключение устройств, управление пользователями и подписками, Telegram-прокси, WARP-обход блокировок и типовые проблемы.

## Как это устроено

Каждая нода обслуживает только своё имя `vpn-<имя>.<домен>` и общее `tg.<домен>`. Цепочка на порту 443:

```
SNI vpn-<имя>.<домен> → gerbil → traefik (passthrough) → Xray :9446 → VLESS | заглушка :9447
SNI tg.<домен>        → gerbil → traefik (passthrough) → mtproto :8446 → Telegram | заглушка :8448
SNI rem.<домен>       → gerbil → traefik → панель Remnawave (ресурс Pangolin, см. pangolin.md)
```

VPN-клиент с ключом попадает в туннель, Telegram-клиент с секретом — в прокси, случайный гость видит обычную страницу-заглушку с доверенным сертификатом. Правила passthrough лежат отдельным файлом `/opt/pangolin/config/dynamic/mask_config.yml` — Pangolin их не затирает.

| Порт | Что | Доступ |
|---|---|---|
| 443/tcp | маскировка (gerbil → passthrough) | из интернета |
| 2087/tcp | запасной VPN-канал (инбаунд добавляется в панели вручную) | из интернета |
| 9446 | Xray: VLESS+TLS+fallback | только из docker-подсети |
| 9447 | nginx-заглушка VPN (обычный http: TLS терминирует Xray) | только с Xray |
| 8446 | mtproto.zig | только из docker-подсети |
| 8448 | nginx-заглушка Telegram (ssl) | только с mtproto |
| 2099 | remnanode (панель подключается к ноде) | только из docker-подсети |

Важно: каждое имя `vpn-<имя>` должно вести на IP своей ноды. Общий wildcard здесь не годится: чужая нода отдаст 404 и сертификат другого имени — дыра в маскировке.

## Режимы панели

Установщик (`remnawave`) спрашивает режим через `REMNAWAVE_MODE`:

- `install` — панель на control-ноде: compose в `/opt/remnawave/`, PostgreSQL кластера (VIP `10.66.0.99:5433`), Valkey по unix-сокету. Люди заходят на `https://rem.<домен>` (ресурс Pangolin), ноды ходят к панели по сети кластера. Падение control-ноды не роняет VPN: Xray работает по закешированному конфигу, панель поднимается на другой ноде за минуты (база уже там).
- `connect` — панель на домашнем сервере за серым IP: локально ничего не ставится, ноды только регистрируются. Нужны сайт `cluster-home` с Newt (`install/home-newt.sh` в домашнем LXC), ресурс `rem.<домен>` и API-токен в `install/secrets/remnawave-api.token`.

Повторный запуск шага идемпотентен: существующие ноды, ключи и пользователи не пересоздаются. Шаг можно повторить отдельно: `bash /opt/321r/install/install.sh --from=remnawave --to=remnawave`.

## Подключение устройства

1. Страница подписок (с QR-кодами и кнопками клиентов): `https://sub.<домен>/<shortUuid>`.
2. Сырой URL для VPN-приложений (base64): `https://rem.<домен>/api/sub/<shortUuid>`.
3. Клиенты: Hiddify, v2rayNG, Streisand и аналоги — «добавить подписку» и вставить URL.

Подписка отдаёт VLESS+TLS конфиги для каждой ноды на порту 443. Корень `https://sub.<домен>/` намеренно «молчит» (502) — страница живёт только на путях `/<shortUuid>`, это защита от проверяющих; ошибкой это не является. Браузеру показывайте UI-ссылку, приложениям — сырую.

## Пользователи и подписки

- Панель: `https://rem.<домен>`, логин `admin`, пароль — в `/etc/db/secrets/remnawave-admin.json` на первом сервере. Важно: смените пароль (минимум 24 символа и спецсимволы) и включите 2FA.
- Новый пользователь: Users → «+» → имя и срок действия (срок обязателен) → сквад `321r`. Ссылка подписки: `https://sub.<домен>/<shortUuid>`.
- Без Internal Squad подписка честно пишет «No hosts found» — назначьте пользователю сквад.
- Пользователь `hc-probe` служебный (health-check страницы подписки) — не удаляйте его.
- Страница подписок — отдельный сервис `remnawave/subscription-page` на control-ноде (`127.0.0.1:3010`) со своим API-токеном `321r-subpage`. С обычным User-Agent она отдаёт base64, браузеру — HTML.

## Telegram-прокси

Прокси mtproto.zig работает на каждой ноде под маской `tg.<домен>`; секрет один на кластер, клиенты ходят на любую ноду через мульти-A DNS. Ссылка для Telegram:

```
tg://proxy?server=tg.<домен>&port=443&secret=...
```

Важно: `secret` в ссылке — FakeTLS-формат (префикс `ee` + секрет + hex-код домена), а не исходный 32-hex. Сырой секрет даёт «недоступен». Берите готовую ссылку командой `mtbuddy links` на любой ноде или из памятки владельца. Ещё несколько правил:

- Маска Telegram — `tg.<домен>`, не apex-домен: NS-делегирование `_acme-challenge` не пропустит certbot для apex (см. [dns-and-tls.md](dns-and-tls.md)).
- mtbuddy при установке открывает порт 8446 наружу; штатная установка убирает это правило и открывает порт только от docker-подсети.
- Звонки Telegram через MTProto-прокси не идут — ограничение протокола.
- `mtbuddy uninstall` удаляет каталог `/opt/mtproto-proxy` вместе с конфигом — выгружайте конфиг заранее.

## WARP-обход блокировок

Для трафика mtproto используется Cloudflare WARP (обфусцированный WireGuard) — штатный механизм mtproto.zig `[upstream].type = "tunnel"`: в туннель идут только сокеты прокси (SO_MARK=200), маршруты к DC Telegram прокси проверяет сам.

```bash
/usr/local/bin/warp-321r.sh status          # состояние туннеля
/usr/local/bin/warp-321r.sh up              # включить обход
/usr/local/bin/warp-321r.sh down            # выключить (mtproto напрямую)
/usr/local/bin/warp-321r.sh set-config файл.conf   # замена конфига с проверкой и откатом
```

- Конфиг WARP — свой на каждую ноду: `/etc/amnezia/amneziawg/warp.conf`. Один файл на кластер запрещён: установщик отклоняет совпадающие конфиги. Загрузка — переменные `WARP_CONF_<имя>` в инвентаре или замена через бота (раздел «WARP/mtproto»).
- `set-config` проверяет туннель по рукопожатию и трассе до Cloudflare и сам откатывается при неудаче. Проверять надо именно трассу: отчёт mtbuddy может быть оптимистичным при битом endpoint.
- Своя маршрутизация через iptables/ip rule не нужна и вредна: owner-матч на некоторых ядрах ловит почти весь трафик ноды.
- Служба `warp.service` поднимает обход при старте системы.

## Проверка

```bash
# маска отвечает как обычный сайт — проверяйте ОБЯЗАТЕЛЬНО браузером, не только curl
curl -sI https://vpn-<имя>.<домен>/
# http-запрос должен уходить на https (301)
curl -s -o /dev/null -w '%{http_code} %{redirect_url}' http://vpn-<имя>.<домен>/
# приёмка подписки без изменений (запускать с первого сервера)
python3 /opt/321r/scripts/remnawave-mask.py --mode install --panel-url https://rem.<домен> \
  --domain <домен> --node <имя1> --node <имя2> --check-only
```

## Где лежат секреты

| Что | Где |
|---|---|
| Пароль администратора панели | `/etc/db/secrets/remnawave-admin.json` (первый сервер) |
| БД-пароль панели | `/etc/db/secrets/remnawave.env` |
| Секрет ноды (SECRET_KEY) | `/etc/db/secrets/remnanode-<имя>.env` |
| API-токен страницы подписки | `/etc/db/secrets/remnawave-subpage.token` |
| API-токен внешней панели (connect) | `install/secrets/remnawave-api.token` на сервере установки |
| Секрет Telegram-прокси | `install/secrets/mtproto-secret` на сервере установки |
| Пробная подписка | `/etc/db/secrets/remnawave-probe-url` |
| Сертификаты маскировки | `/etc/letsencrypt/live/mask/` (симлинк, certbot, автопродление) |

## Частые проблемы

| Симптом | Причина | Лечение |
|---|---|---|
| Браузер обрывает соединение, а curl отвечает 200 | Браузер договаривается об HTTP/2, а fallback отдаёт HTTP/1.1 | В инбаунде маски обязателен `alpn: ["http/1.1"]`; проверяйте маску браузером |
| 404 при открытии адреса без `https://` | Запрос идёт на :80 без редиректа | В `mask_config.yml` обязателен http→https-редирект для каждого домена маски |
| Подписка: «No hosts found» | У пользователя не назначен Internal Squad | Назначьте сквад `321r` |
| API отвечает 403 или рвёт соединение | JWT работает только с заголовком `X-Remnawave-Client-Type: browser`; прямые запросы к `127.0.0.1:3000` отбрасываются | Зовите API через `https://rem.<домен>`; для автоматизации — API-токен со `scopes: ["*"]` |
| Telegram-прокси «недоступен» | В ссылке сырой секрет вместо FakeTLS | Возьмите ссылку из `mtbuddy links` |
| Одна из нод отдаёт 404 или чужой сертификат | A-запись `vpn-<имя>` ведёт не на ту ноду | Поправьте DNS: каждое `vpn-<имя>` — на IP своей ноды |
| Xray в краш-цикле после правки профиля | В Xray 26.x во всех vless-settings нужно `"decryption": "none"` | Исправьте профиль в панели — ноды пересоберут конфиг сами |
| Панель недоступна, но VPN работает | Норма: ноды держат конфиг в памяти | Восстановите панель (см. [databases.md](databases.md)); обновления подписок подождут |
