# Поиск и устранение неисправностей

Формат каждого случая: **симптом → вероятная причина → лечение**. Команды проверены по коду
установщика и скриптов; точные имена, пути и порты сохранены. Если симптома нет в списке —
сначала быстрая диагностика ниже, потом разбор по слоям: [pangolin.md](pangolin.md),
[databases.md](databases.md), [amnezia-wg.md](amnezia-wg.md).

## Шаг первый: `321r-doctor.sh`

На любой ноде кластера:

```bash
/usr/local/bin/321r-doctor.sh
```

Один текстовый файл `/root/321r-diagnostika-<дата>.txt`: состояние всех нод, слой БД и его
согласованность, меш, бэкапы, мониторинг, фрагменты журналов — и в конце готовый список
находок. Секреты (пароли, токены, ключи) вырезаются автоматически, файл можно спокойно
прикладывать к обращению в поддержку. `--no-logs` — короткий отчёт без журналов;
код выхода 1 означает, что находки есть (можно вешать на cron).

## Быстрая диагностика «одной вставкой»

```bash
# снаружи (с рабочей машины), по всем IP нод:
for ip in <ip1> <ip2> <ip3>; do
  curl -sk --connect-timeout 6 --resolve <имя>:443:$ip https://<имя>/ -o /dev/null -w "via $ip: %{http_code}\n"
done
# на ноде:
docker ps --format '{{.Names}}\t{{.Status}}' | sort
journalctl -t db-guard -n 30 --no-pager
wg show | grep -E 'peer|latest handshake'
ip -4 addr show wg0        # 10.66.0.X + VIP 10.66.0.99
```

Коды `curl`: `0` — ок; `7` — connection refused (порт закрыт, служба мертва); `28` — timeout
(режут, фенс, туннель); `60` — сертификат (для диагностики добавьте `-k`).

## Веб-ресурсы Pangolin

### «404 page not found» на ресурсе

Три разных причины с одной маской:

1. **Цель unhealthy → маршрутизатор отсекает её.** Health-check создан неполным (UI-мастер!)
   или не настроен вовсе. → Полный набор HC-полей через API (`POST /api/v1/target/{id}`) —
   см. [api.md](api.md). Важно: цель БЕЗ строки HC тоже отсекается (NULL в базе ≠ «unhealthy»).
2. **Агент (Newt/CLI) со старым конфигом** — после удаления/пересоздания ресурсов он живёт
   старым списком целей до синхронизации. → Перезапуск агента на клиенте или смена секрета
   сайта (агент переподключится и подтянет конфиг).
3. **Маршруты между нодами не сошлись** (туннель держит одна нода, другие пересылают; после
   ребутов сходимость 1–2 мин). → Подождать или перезапустить gerbil на «отстающей» ноде.

Признак различия: `000`/таймаут через одну ноду — почти всегда случай 3.

### «503 no available server» (traefik)

За туннелем никто не слушает порт цели: агент не подключён, порт цели мёртв или агент с
устаревшим internalPort. → Проверить сайт в панели (online?), лог агента на клиенте
(ищите `Sync: adding TCP target ...`), HC цели.

### Сертификат «TRAEFIK DEFAULT CERT», ресурсы 404

Известные баги Pangolin v2.3.4 (двойная `*.`, плейсхолдер «Server IP Address», залипший
статус `failed`). → `pangolin-wildcard-repair.sh <ip>`; после каждого рестарта pangolin.
Подробно — [pangolin.md](pangolin.md) и [dns-and-tls.md](dns-and-tls.md).

```bash
/usr/local/bin/pangolin-wildcard-repair.sh <ip-ноды>
```

### «Domain is not verified» при создании ресурса

Тот же плейсхолдер в `dnsRecords.value`. → repair-скрипт; для config-доменов (`domains:` в
config.yml) валидация не нужна — `verified=true` сразу.

### Работает через один IP, не работает через другой

Кросс-маршрутизация или здоровье цели. Проверка по каждому IP:

```bash
curl -sk --resolve <имя>:443:<ip> https://<имя>/ -o /dev/null -w "via <ip>: %{http_code}\n"
```

→ Смотреть HC цели и сходимость маршрутов (случай 3 выше).

### traefik/gerbil: 000 или EOF после рестартов

traefik живёт в `network_mode: service:gerbil` — одиночный `docker restart gerbil` оставляет
traefik в осиротевшем netns. → Пересоздавать их только вместе:

```bash
cd /opt/pangolin && docker compose up -d --force-recreate gerbil traefik
```

Важно: для перечитывания динамических конфигов traefik достаточно `docker restart traefik`
(gerbil не трогать). Одиночный перезапуск gerbil запрещён.

### Ingress ноды мёртв после пересоздания gerbil (не отвечает даже маска)

gerbil без конфига панели не даёт маппинги, а traefik живёт в netns gerbil. → Порядок
восстановления: **сначала здоровая панель, потом gerbil/traefik** (вместе, команда выше).

## Docker и образы

### Образ не скачивается с Docker Hub (pull висит)

Иногда с конкретной ноды стопорятся слои большого образа (маленькие тянутся, большой — нет).
Не ждите часами: перенесите образ по мешу от соседа, где он уже есть (быстро и детерминированно):

```bash
# на мастере или любой ноде; имя образа — своё
ssh root@<mesh-IP-донора> 'docker save <образ> | gzip -1' | ssh root@<mesh-IP-приёмника> 'gunzip | docker load'
```

Внимание: у приёмника не должно быть `ssh -n` — этот флаг перенаправляет stdin в `/dev/null`
и обрезает поток («gzip: unexpected end of file»). Установщик качает образ только когда его
нет локально, поэтому после переноса повторный запуск шага проходит мгновенно.

## Базы данных

### «read-only transaction» при записи в PG

Вы пишете в стендбай. → Только через VIP `10.66.0.99:<порт>` (он ведёт на первичного).

```bash
. /etc/db/secrets/<app>.env
docker exec -e PGPASSWORD="$POSTGRES_PASSWORD" pg-<app> psql -h 10.66.0.99 -p <порт> -U postgres
```

### `FATAL: requested timeline N is not a child of this server's history` (краш-цикл)

Штатный случай после ребут-шторма: диск стендбая отстал, таймлайн разошёлся. →
`pg-rebuild-standby.sh [app]` на больном узле (~1 мин, сам найдёт первичного через VIP).

```bash
/usr/local/bin/pg-rebuild-standby.sh pangolin    # app по умолчанию — pangolin
```

Важно: после любых правок скриптов раскатывать их на ВСЕ ноды — лечение старой версией
падает.

### Стендбай часами спамит «requested starting point ... is not in this server's history»

Тот же разошедшийся таймлайн, но без краш-цикла. → Штатное `pg-rebuild-standby.sh`.

### `FATAL: remaining connection slots are reserved`

`max_connections` мал (норма — 200, вшито в `db-add.sh`). → Для живого инстанса: правка
конфига + рестарт в окно; новые инстансы — только через `db-add.sh`.

### `pg-rebuild-standby.sh` удалил данные и упал на авторизации

Порт VIP захардкожен (5432), а приложение живёт на другом порту (например, 5433). → Порт
берётся из `/etc/db/apps.d/<app>.yaml` — убедитесь, что на ноде свежая версия скрипта и
реестр на месте. Правило: скрипты восстановления обязаны читать порт и имена из реестра.

### Mongo: член реплика-сети завис, отстал или не вступает

Аналог «разошедшегося таймлайна» PostgreSQL. Лечение такое же штатное: член пересоздаётся,
данные догоняются сами (initial sync).

```bash
/usr/local/bin/mongo-rs.sh status <app>            # кто в составе и в каком статусе
/usr/local/bin/app-member.sh remove <app> <узел>   # убрать больного члена
/usr/local/bin/app-member.sh add <app> <узел>      # и ввести заново
```

### Контейнер «жив, но мёртв» (unhealthy, рестарта нет)

Docker перезапускает только ПАДШИЕ контейнеры. → `unhealthy-restart.sh` (cron каждую минуту)
лечит это автоматически; вручную: `docker restart <имя>`.

### Mongo молчит / «сел по памяти»

`mongosh` внутри контейнера mongod убивал базу по OOM. → Только отдельным контейнером:

```bash
docker run --rm --network host mongo:7 mongosh \
  "mongodb://10.66.0.99:27017/?replicaSet=rs_komodo" --quiet --eval 'rs.status().members.map(m=>m.name+":"+m.stateStr)'
```

### `mongod` в crash-loop: «BadValue … cacheSizeGB»

MongoDB не принимает `wiredTigerCacheSizeGB` меньше 0.25 — ужатие кэша арбитра до 0.1 кладёт
контейнер. → Вернуть 0.256; экономить на mongo можно только через `mem_limit`, и не ниже 640m.

### cgroup-OOM убивает mongosh или postgres (dmesg: «Memory cgroup out of memory»)

Пик mongosh ~200 МБ поверх кэша mongod; у PG бэкенда пик упирается в `mem_limit`. →
`mem_limit` mongo — 640m всем (арбитр держит ~383 МБ); PG-панели — 512m:

```bash
docker update --memory 512m pg-pangolin
dmesg | grep -i oom
```

Важно: живые правки `docker update` не попадают в compose — при пересоздании инстанса лимиты
откатятся. Всё важное — только в compose/шаблонах.

### Панель Pangolin работает «через раз», ресурсы пропадают или «исчезают»

- **Симптомы:** дашборд открывается не всегда; ресурсы эпизодически 404/503; в логе панели
  `57P03 cannot_connect_now`, `Failed to fetch active domains from traefik config`.
- **Причина:** переключение первичного PostgreSQL (db-guard промоутил другую ноду) — панель
  в момент смены получает 57P03 и не может построить traefik-конфиг. Частый спутник —
  старый первичный не может вернуться стендбаем («timeline N is not a child»).
- **Лечение (штатное, ~1 мин):** `pg-rebuild-standby.sh pangolin` на кашляющей ноде; в логе
  появится «started streaming WAL ... on timeline N». Проверка: 57P03 нет, `pg_stat_replication`
  полон. После любого переключения БД давайте 1–2 мин на сходимость и проверяйте панель.

### Панель показывает «Результаты не найдены» при живых данных

- **Симптом:** списки ресурсов пустые, хотя в базе записи есть; запрос списка ресурсов
  деградирует до 10+ секунд.
- **Причина:** тяжёлый план запроса (битая статистика, JIT) → панель отменяет запрос по
  таймауту (в логе `57014 query_canceled`) и молча показывает пустой список.
- **Лечение:**

```sql
ALTER DATABASE pangolin SET jit = off;
ANALYZE;
```

Запрос падает с секунд до миллисекунд. Профилактика: `jit=off` и `mem_limit 512m` вшиты в
`db-add.sh`; `ANALYZE` после крупных правок базы; следить за `uptime` слабых нод.

### Нагрузка (load) 4–5 при видимом простое, ядро ест CPU

Частые тяжёлые проверки: `mongosh` (старт ~1–2 с CPU) и `docker node update` на тике
db-guard, огромные логи mongo. → Диагностика и лечение:

```bash
top -bn2 | head
vmstat 1 3                                        # столбцы us/sy/wa
du -h /var/lib/docker/containers/*/*-json.log
```

Лечение: кешированные проверки в db-guard (уже в коде), тик 10 с, logrotate,
`vm.swappiness=10`. Проверка: load падает в течение 5–15 минут.

### Прокси не переключился после промоушена

Перезагрузить прокси правильно: `docker restart` (НЕ `docker kill -s USR1` — команда
интерпретируется как «остановлен»).

### В `postgresql.auto.conf` копятся дубли `primary_conninfo`

PostgreSQL берёт последнюю строку, поэтому работало, но мусор кочует через `pg_basebackup`
на новые стендбаи. → Перед записью удалять старое: `sed -i '/^primary_conninfo =/d'` (так
сделано в `pg-rebuild-standby.sh`, `db-add.sh`, `db-guard.sh`); накопленные строки вычистить
и выполнить `pg_reload_conf()`.

### БД «выделяется» из строя остальных

Расхождение настроек между инстансами: где-то `max_connections=20`, jit включён,
`mem_limit 200m` — при норме 200/jit-off/512m. Причина — инстанс поднимали вручную, мимо
`db-add.sh`. → Выравнять настройки и правки внести в compose. Правило: всё важное — только
через `db-add.sh`/шаблоны; регулярно сверять инстансы между собой.

### db-guard: что смотреть

```bash
journalctl -t db-guard -n 30 --no-pager
```

Маркеры в логе: `ПРОМОУШЕН`, `метка перехвачена`, `ФЕНС`, `ФЕНС снят`, `КВОРУМ ПОТЕРЯН`,
`КВОРУМ ВОССТАНОВЛЕН`, `апстрим прокси →`, `инстанс не отвечает`. В штатном режиме db-guard
молчит — пишет только назначения, переключения прокси и фенс.

### Аварийный режим промотнул стендбай при живом кластере

- **Причина:** предохранитель проверял живость первичного на неверном уровне (нет пароля →
  запрос молча падал = ложное «первичного нет»; либо TCP-проверка — haproxy принимает
  handshake даже с мёртвым бэкендом).
- **Правило:** interlock обязан быть fail-safe (неизвестность = не трогаем), а живость
  первичного проверяется ТОЛЬКО на уровне протокола приложения: `SELECT NOT pg_is_in_recovery()`
  через VIP с паролем из secrets. В актуальном `db-guard.sh` так и сделано: «через VIP отвечает
  ЖИВОЙ первичный — аварийный промоушен отменён».
- **Возврат после аварийного режима:** строго «шаг назад» или пересборка стендбаев
  `pg-rebuild-standby.sh`; сверить целостность данных.

### Восстановление PG из basebackup: подводные камни

1. Пути контейнера и хоста различаются (`/var/lib/pgwal` в контейнере — уже каталог
   приложения): проверять, что копирование скопировало непустой набор.
2. Basebackup со СТЕНДБАЯ даёт неполный WAL (стендбай не генерирует записи) — восстановление
   упирается в `must specify "restore_command"`. Брать basebackup только с первичного через VIP.
3. `pg_wal.tar.gz` распаковывать в `pg_wal/` (сегменты в архиве лежат без префикса пути).
4. Копия стендбая содержит `standby.signal` — убрать его, добавить `recovery.signal`.
5. `recovery_target='immediate'` требует `restore_command='false'` («архив пуст») — иначе PG
   не может решить, «раннейшая» ли это точка.
6. PG не стартует с `max_connections` меньше, чем в контрольном файле первичного — запускать
   scratch-инстанс с продовыми `-c max_connections=200`.

## Меш и сеть

### Пир меша не поднимается

1. DNS-имя endpoint'а резолвится в старый IP → ждать reresolve (45 с) или `reresolve-dns.sh wg0`.
2. HPK (HeaderProtectionKey) различается между нодами — обфускация не сходится.
3. Модуль `amneziawg` не загружен: `dkms status`, `modprobe amneziawg`.
4. Не тот порт: меш — 51821, gerbil — 51820.

### Сервис недоступен из мира, из mesh — работает

DOCKER-USER режет публикацию (внимание: порт там — КОНТЕЙНЕРНЫЙ!) или ufw. → Сверить
`iptables -L DOCKER-USER -v -n` с контейнерным портом; помнить про фенс-правила (позиция 1)
и что `docker-user.sh` их стирает.

### Правило файрвола «не работает» — блок в DOCKER-USER не матчится

DNAT на PREROUTING переписывает порт на контейнерный (host 443 → контейнер 8443) ДО цепочки
DOCKER-USER — правило `DROP dpt:443` не увидит ни одного пакета. Правило: docker-порты
блокировать по КОНТЕЙНЕРНОМУ порту в DOCKER-USER (443→8443, 80→80); host-порты без маппинга
(2087, 8446, 2099) — через INPUT. Проверять всегда по счётчикам:

```bash
iptables -L DOCKER-USER -v -n      # pkts у правил должны расти
```

### `ufw delete` удалил не то правило

По спецификации с портом матчится не только action. → Удалять только по номеру:

```bash
ufw status numbered
ufw delete <N>
```

### Маскировка «светится» — порт 8446 (mtproto) открыт наружу

Правила `8446/tcp ALLOW Anywhere` быть НЕ должно (должно быть только `8446 ALLOW 172.16.0.0/12`).
→ `ufw status numbered` и удалить правило по номеру. Важно: mtbuddy после переустановки может
открыть порт снова — проверять после каждой установки.

### В /var/log/ddns.log «ddns: не удалось узнать свой IP», A-записи не обновляются

Внешние сервисы определения IP недоступны. → В актуальном `ddns.sh` есть фолбэк: IP берётся с
интерфейса (docker-подсети отфильтрованы). Проверка: прогон `bash /usr/local/bin/ddns.sh`
молчит (rc=0).

### Из РФ не открывается, из-за рубежа — открывается

Блокировка IP. → Смена IP ([replace-node.md](replace-node.md)), вход через другие IP
(multi-A) и запасные порты 8443/2053; для людей — VPN-слой ([vpn.md](vpn.md)).

## SSH и доступ

### Забанен fail2ban

```bash
fail2ban-client set sshd unbanip <ip>    # с другого адреса или через консоль провайдера
```

Игнор-лист: localhost + 10.66.0.0/24.

### Остался только парольный доступ / потеряны ключи

Консоль провайдера → `authorized_keys` вручную. Правило: сначала подтверждаем ключевой вход,
потом отключаем пароль. Ключевой вход и порт 2222 проверяет автоприёмка
([operations.md](operations.md)).

## Pangolin и панели

### После правки БД pangolin «откатил» изменения

Синхронизация при старте пересоздаёт записи из конфига (плейсхолдер dnsRecords). → Не
рестартовать pangolin после ручной правки; repair-cron долечит.

### Команда `pangctl clear-certificates` удалила хорошие сертификаты

Известная особенность: сносит все строки. → Перевыпуск через repair-скрипт; не использовать
без нужды.

### Агент на клиенте не синхронизируется

Лог агента: искать `Sync:`/`Websocket connected`. → Рестарт агента или смена секрета сайта
(учётные данные в панели Sites).

## Маскировка секретов перед показом

```bash
<команда> 2>&1 | sed "s/[A-Za-z0-9_-]\{20,\}/СКРЫТ/g"
```

Не показывайте выводы команд и памятку владельца в чатах и скриншотах без маскировки —
подробнее [security.md](security.md).
