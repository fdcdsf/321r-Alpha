# Мониторинг и алерты

Мониторинг 321r устроен в три кольца: самолечение на нодах, собственный надзор из кластера и внешний взгляд из интернета. Основной канал уведомлений и управления — Telegram-бот: алерты приходят с готовым действием, а тишина означает норму. Этот документ описывает, что именно проверяется и что делать с каждым типом алертов.

## Три кольца наблюдения

1. **Внутреннее** (на нодах): `unhealthy-restart.sh` каждую минуту перезапускает зависшие контейнеры, `db-guard` проверяет базы каждые 10 секунд, `pangolin-wildcard-repair.sh` чинит сертификаты. Это иммунитет: система лечится без человека.
2. **Собственное** (Uptime Kuma в кластере): видит сервисы изнутри.
3. **Внешнее** (из интернета, минимум с двух точек): облачный внешний мониторинг + домашний сервер как независимый наблюдатель. Оно ловит то, чего не видят первые два кольца: блокировки, падение DNS, смерть всего кластера.

## Дозор: `tg-watch.sh`

Каждый час на каждой ноде (cron `/etc/cron.d/321r`). При норме молчит, при проблеме шлёт алерт «ДОЗОР».

| Проверка | Порог |
|---|---|
| Диск `/`, `/var/lib/dbdata`, `/var/lib/backup-repos` | занято ≥ 85% |
| Память | свободно ≤ 100 МБ |
| Нагрузка | load(5) > 2 × ядер |
| Сертификат маски (certbot) | до истечения ≤ 14 дней |
| Свежесть бэкапа (`/var/lib/pgbackup/last_ok`) | нет бэкапа или старше 26 ч |
| Верификация восстановления (`last_verify`) | старше 8 дней |

Повторы подавляются: алерт уходит при изменении проблемы и не чаще раза в 12 часов, пока она сохраняется. Режим `tg-watch.sh --check` только печатает проблемы — его зовёт утренний дайджест.

## Утренний дайджест: `tg-digest.sh`

Каждое утро в 09:00 с control-ноды приходит одна сводка: короткий статус каждой ноды и список проблем (или «всё ок» одной строкой). Статусы собирает `tg-info.sh <команда>` — `status`, `disk`, `db`, `backup`, `certs`, `services`, `app <имя>`. Эти же команды можно вызвать вручную на любой ноде.

## Алерты в Telegram

- Алерты шлёт **любая** нода (`tg-alert.sh` — простой curl, без лидера): уведомления переживают смерть любой машины. Формат: `321r · <нода>: <текст>`.
- Формат алерта — с готовым действием: детект делает автомат, действие — одна команда или кнопка в боте. Тишина = норма: шлём только про «надо пошевелиться».

| Событие | Что делать |
|---|---|
| «БЭКАП С ОШИБКАМИ» | `tail -n 50 /var/log/backup321r.log`, затем ручной прогон `backup-321r.sh` ([backups.md](backups.md)) |
| «МАЯК: ПРОТУХ» | проверить cron и диск, запустить прогон вручную |
| «ВЕРИФИКАЦИЯ БЭКАПОВ УПАЛА» | см. рецепт восстановления ([backups.md](backups.md)) |
| ДОЗОР: диск/RAM/load | расчистка, перенос данных ([operations.md](operations.md)) |
| ДОЗОР: сертификат истекает | продлить сертификат ([dns-and-tls.md](dns-and-tls.md)) |
| db-guard: ПРОМОУШЕН | первичный сменился — проверить приложение ([databases.md](databases.md)) |
| db-guard: ФЕНС | нет кворума Swarm; если затянулось — аварийный режим ([doctrine-3-2-1.md](doctrine-3-2-1.md)) |
| Нода не отвечает | замена ноды ([replace-node.md](replace-node.md)) |

## Telegram-бот: панель управления

- Команды принимает control-нода (`tgbot.service`), данные о нодах собирает по SSH (порт 2222).
- Меню на кнопках: 📊 Статус, 🟢 Внешние точки, 🧩 Приложения, 📦 Контейнеры, 💾 Бэкапы, 🗄 Базы данных, 🖥 Серверы, 📜 Логи, 🛡 WARP/mtproto, ⚙ Действия, ℹ Помощь.
- Опасные действия (перезапуск, выгрузка, аварийный режим, перенос инстанса) — только через экран подтверждения с кнопками ✅/❌.
- Данные показываются из снимка: он обновляется раз в сутки или кнопкой «🔄 Обновить». Новое на серверах появляется после обновления.
- Текстовые команды работают как алиасы: `/start`, `/menu`, `/help`, `/status`, `/services`, `/backup`, `/db`, `/disk`, `/logs`, `/apps`, `/containers`, `/warp`, `/ping`, `/restart <контейнер>`.
- Экран 🛡 WARP/mtproto: включение и выключение, статистика, замена конфига — пришлите файл `.conf` боту после соответствующего запроса.

## Uptime Kuma

Стек `swarm/stacks/uptime-kuma.yaml` (задача на одной из нод, порт 3001 через Swarm ingress). Размещение — любая нода, кроме узла с ролью `state`: смерть ноды не убивает мониторинг. UI вынесен наружу ресурсом Pangolin; порт 3001 из интернета закрыт цепочкой DOCKER-USER ([security.md](security.md)). Состояние хранится в SQLite-томе: при переезде история пуста.

Начальный набор мониторов:

| Монитор | Тип | Что проверяет |
|---|---|---|
| dashboard-pangolin | HTTP(s) | `https://pangolin.<домен>/` |
| komodo | HTTP(s) | `https://komodo.<домен>/` |
| ресурсы по списку | HTTP(s) | каждый `*.<домен>`, по каждому IP ноды |
| noda-*-ping | Ping | mesh-адреса нод |
| backup-freshness | Push | push от cron бэкапов; нет push за 24 ч — алерт |

## Домашний сервер как наблюдатель

```bash
# cron на домашнем сервере, каждые 5 мин:
dig +short dns.<домен> | wc -l          # ожидание: 3 адреса
curl -sf --max-time 10 https://pangolin.<домен>/ -o /dev/null || <телеграм-алерт>
```

Домашний сервер не в критическом пути — он только стучит в колокол.

## Кто следит за следящим

- Раз в месяц намеренно ломайте тестовый ресурс и убеждайтесь, что алерт пришёл.
- Проверяйте push-мониторы Kuma и статус-дашборд внешнего мониторинга.
- Полноценный слой надзора с историей и графиками даёт Zabbix ([zabbix.md](zabbix.md)).
